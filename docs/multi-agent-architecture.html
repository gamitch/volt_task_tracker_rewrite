Engineering Architecture Note

A governed multi-agent development system

How the VOLT Team Portal is built by a hierarchy of AI agents under a written constitution — with risk-tiered process, adversarial pre-dispatch review, executable verification harnesses, and an event-driven pipeline that runs from a Linear card to a merged, CI-green pull request without a human in the loop.

Repository gamitch/volt_task_tracker_rewrite Subject the development system, not the product State of record 11 August 2026

This document describes the machine that builds the app, not the app itself. The product is a private, role-aware attendance and volunteer-hours portal for a high-school robotics team — a small application by any measure. The system that produces it is not small, and it is the interesting artifact: a nine-role agent hierarchy with per-role model tiers, a 769-line constitution where nearly every rule is a written-down post-mortem, three process tiers selected by risk rather than by ticket size, six executable verification harnesses that agents are required to run rather than reason about, and a webhook chain that turns dragging a card into Todo into an agent claiming that issue and opening a pull request.

The through-line is a single design commitment, and everything else follows from it: no agent may certify its own work, and no claim counts as evidence until something was executed and observed. Every mechanism below exists either to enforce that, or to make it affordable.

Section 01The system at a glance

Work moves through three planes. Intake decides what gets worked and when — a human gesture in Linear is the only trigger. Execution is the agent hierarchy: an orchestrator chooses how much process a change deserves, then delegates to specialist roles that cannot grade themselves. Verification and record is where a change has to survive: six local gates, four independent CI job graphs, and a written record that is committed in the same commit as the code it describes.

Section 02The agent hierarchy

Nine roles, each defined as a prompt file in .claude/agents/ with its own tool grant and a pinned model. The pin is the point: nobody selects a model by hand, and a role's cost profile is a property of the role rather than of the operator's mood. A test checker that shells out to npm run test runs on the cheapest tier available; an adversarial reviewer that has to find the flaw in someone else's reasoning runs on the most capable one.

RoleModel pinTool grantCharter
boss-architectfableread, write, edit, bash, agentOwns the constitution and architectural decisions; performs final milestone acceptance. Explicitly not for routine coding.
boss-arbiterfableread, write, edit, bashDecides worker-vs-checker disputes: redo, checker was wrong, spec ambiguous, constitution needs clarifying, or escalate to the human.
foreman-plannersonnetread, write, edit, agentConverts approved plans into small packets, tracks attempts, and — critically — prevents context bloat by never handing a worker the full record.
checker-premiseopusread, glob, grep, bashFact-checks a plan against the real codebase before dispatch. Attacks the author's declared least-confident decisions first.
worker-implementersonnetread, write, edit, bashImplements exactly one narrow task inside its packet's allowed files. Upgraded to opus per dispatch when the task touches migrations, RLS, metric SQL, or auth.
checker-revieweropusread, glob, grep, bashGrades completed work against the packet's acceptance criteria and the constitution. Read-only by design — it cannot fix what it finds.
checker-testshaikuread, bash, glob, grepRuns the deterministic commands. Deliberately the cheapest role in the roster, because its judgement is an exit code.
checker-accessibilitysonnetread, bash, glob, grepKeyboard paths, semantic HTML, visible focus, contrast, light/dark. A keyboard failure on a core flow is a BLOCKER, not a nit.
checker-contentsonnetread, glob, grepProtected wording, factual claims, citation fidelity. The narrowest tool grant in the system — it cannot even run a command.

Three mechanisms decide which model runs

They compose, and confusing them has cost real money:

  1. Frontmatter pins. Spawning a role reads its model: field. This is why model selection "just works" in an interactive session — the pins do it, not the orchestrator's judgement.
  2. The per-dispatch override. Constitution item 18 requires the orchestrator to pass model: "opus" on the call when a task creates or edits a migration, an RLS policy or security definer helper, metric-view SQL, or auth/session/role logic. It cannot live in config, because the trigger depends on what the task turns out to touch.
  3. The orchestrator's own model, set by whoever launches the session — or, in the automated dispatch path, keyed to the issue's tier label: frontier for heavy and unreviewed (where the tier judgement itself decides every downstream cost), balanced for standard and fast.
Measured failure — and the reason this is written down

All three mechanisms depend on the orchestrator being able to spawn subagents. In an automated run, --allowedTools replaces the default tool set rather than extending it, and an allowlist that forgets the subagent tool silently removes delegation. Nothing reports it: the run starts, thinks, works, and produces a plausible result with one model playing every role. On 2026-08-10, issue GAM-304 was dispatched as tier/unreviewed, self-judged HEAVY on an RLS write path — item 18's exact trigger — and ran the entire chain on a single balanced primary with no ability to delegate any of it. It died at turn 81 having produced no branch, no commit and no PR. Three constitution items become unsatisfiable rather than merely skipped in that state, and the tell-tales are now documented: a HEAVY row completing with no premise-gate verdict, an init line naming one model with no subagent ever appearing, and a row that should have delegated exhausting its turn budget.

Section 03Process tiers: paying for risk, not for ceremony

The full chain — packet, premise gate, worker, checker — is expensive. Running it on a one-line bug fix is how a governed process discredits itself. The owner said so directly, and the answer became constitution item 26:

For small fixes like items T321 and T323 is there a faster path we can take to get those done? the Boss→Checker→Foreman→Worker→Checker path seems to eat up alot of time for a few line bug fix Human owner, 2026-08-02 — the authorization for the three-tier model

The tier is chosen by one question, and it is not about ticket size, topic, or how many files are touched: can a mistake here corrupt data, or lie to a user about their own data? The orchestrator must state its choice and defend it in the pull request, so a wrong call is visible and correctable rather than silent.

Why the heavy tier keeps its cost

Two cases, both recorded, both invisible to reading the code. On task T305 the premise gate built the proposed prescription and captured the real upsert payload, proving the fix would have nulled a student's recorded volunteer hours and attendance method. On T189 it proved the proposed detector relied on a view that inner-joins on an active season — so a lapsed season would have told every student their account was deactivated. The rule that generalises from both: a gate that only reads is worth much less than one that runs.

Section 04The constitution as an incident log

docs/swarm/constitution.md is 769 lines and it is not a style guide. Items 1–17 are the project's fixed standards — precedence order, security posture, stack locks, accessibility as a shipping requirement, and an unusual clause forbidding engagement mechanics because the users are minors and volunteers. Items 18–30 are different in kind: each one is a post-mortem that was promoted into a rule, and each carries its own evidence, its authorizing date, and the failure it exists to prevent.

This is the part colleagues tend to find most transferable, so it is reproduced in full below. Read the right-hand column first — the rules are downstream of it.

ItemThe ruleThe incident that produced it
18 Upgrade the worker's model, per dispatch, for migrations, RLS or security definer helpers, metric-view SQL, and auth/session/role logic. These are the four places where a silent error is a data or privacy problem and is hard to detect after the fact. Everywhere else, the worker/checker loop is cheaper than the upgrade.
19 No plan reaches a worker until an adversarial premise checker returns DISPATCH. REVISE is not advisory. Every artifact in the process was checked by someone who did not write it — except plans. A real PRD reached the approval gate carrying two false defect claims, one physically impossible prescription, one "fix" that would have stripped accessible names off six screens, and a silent reversal of a passed task's green test.
19a The gate is capped at two rounds; a third REVISE escalates to the human. Measured: round 1 cost ~130K frontier tokens and caught 4 BLOCKERs; round 2 cost ~105K and caught 2 MAJORs. One round ≈ one prevented rework cycle, so two rounds is break-even-to-positive and a third is net negative. A plan still failing after two rounds has something wrong with the plan, not the wording.
19d Every heavy packet ends with three to five numbered least confident decisions, each naming the decision and what would make it wrong. The gate attacks that list first. Roughly half of round 1's findings were the author's own unverified line numbers and claims — meaning the author was already in a position to know where the weak ground was. Declaring a doubt costs nothing and is never held against the author; concealing one costs a gate round.
20 A deliberate deferral must file a task, not leave a code comment. Comments are not triaged; rows are. Two team pickers shipped rendering fixture data because each task correctly declined out-of-scope wiring and said so only in a comment. Because events.team_ids is uuid[] while the fixture ids were plain strings, that deferral escalated into meeting creation failing outright in production. A light/dark toggle shipped inert for the same reason.
21 Completion reports state a commit SHA, and existence is verified rather than assumed. "Clean" and "committed" are different claims. A worker reported "final state confirmed clean" alongside an accurate account of 770 changed lines, live browser measurements at three viewports, and every command it ran. All of it was real and none of it was committed. Routine worktree cleanup would have destroyed the work; it surfaced only because an empty diff against the merge base contradicted the report.
22 Explicit pathspecs only — never git add -A or git add ., by any agent, ever. A subagent modified a source file without authorization during a documentation commit. A habitual git add -A would have swept that change into a commit whose message described packet authoring — no packet defining it, no checker verifying it, human owner away. Three safeguards bypassed at once, not by defeating them but by staging too broadly.
23 Mutation experiments run in the agent's own git worktree, never the shared tree. Corollary: a dirty tree is not automatically an unauthorized change. A premise gate ran four instrumented mutations against the shared tree, intending to revert each. The orchestrator found the tree dirty mid-experiment, reverted it, and misattributed the change to a different agent that was behaving correctly — three failures from one missing convention. The rule isolates the practice rather than discouraging it: mutation proofs have caught more real defects here than any other technique.
24 Recording a task and merging it are one action. The ledger row and verification entry are updated in the merge commit. Records were backfilled accurately at 11:39. Five tasks then merged over the following ten hours and not one row was updated — so the very document the owner reads to decide whether to merge still said "packet gated" for work already live. A gate had explicitly flagged the gap and it was acknowledged and not acted on. Splitting merge from record means the second step is always optional under pressure, and it is always the one dropped.
25 Proportionality. Grade security findings against this threat model — one volunteer team, no PII stored — not a corporate one. A finding about view semantics was escalated to a security-class task on two bad steps: reading a table-scoped rule as covering views, then grading its own extension as blocker-adjacent. The "exposure" was in fact the product — the leaderboard shows everyone's hours by design. The task closed as no-change. Written verbatim from the owner: "This is a volunteer group, not a company… please keep it simple."
26 Three process tiers triggered by risk, not by topic, ticket size, or habit (§3 above). The full chain was eating hours on few-line fixes. The tier is now a judgement the orchestrator must state and defend in the pull request — so a wrong call is visible rather than silent.
27 A user-visible surface reading from a fixture or stub is Partial, never Passed — and the wiring task is filed and linked before the row moves. Item 20's three failures were one failure seen three times, and every one of them passed a checker — because in each case the checker was asked whether the component rendered, never whether it was connected to anything. Packets for user-visible work now name the real data source as an acceptance criterion, so the checker verifies the connection instead of the render.
28 Work is dispatched from Linear, and claiming it is the first act. Move the issue, then re-read it to confirm you hold it. The first agent dispatched through Linear found its issue correctly and unaided — and then did not claim it. The agent was not at fault: the constitution contained the word "Linear" zero times. The migration moved 296 rows of data and left the protocol behind. Linear has no compare-and-set, so without the read-back there is no claim at all, only a hope.
29 The 301-row markdown ledger is frozen. Linear allocates ids atomically; the git-side record is generated, never maintained. A hand-maintained table failed three independent ways in a single audit: merged, tested, live work with no row at all; a workflow document claiming 40 open rows against a true 50; and eleven rows recording their closure in the wrong column while Status still read "Filed", so an agent worked a row superseded four days earlier. None of it was carelessness — it is what a schema-less table does at 301 rows and four concurrent machines.
30 Every issue an agent writes goes through the linear-task-writing skill: lead with the defect, state and defend a priority, re-verify every citation, preserve the original when rewriting. Owner, verbatim: "i have to know which ones to prioritize and i can't understand what it's saying." Rewriting the trigger issue also surfaced three errors nobody had caught — a wrong line number, a second render site that does not exist, and a missing root cause that would have sent the implementer to the wrong function. The rewrite was not cosmetic; the verification it forced is what found the errors.
The pattern worth stealing

Every one of these rules is cheap to state and was expensive to learn. Writing the incident into the rule is what stops a future agent — or a future engineer — from re-litigating it, and it is why the constitution can be handed to a cold agent as its entire onboarding. The rules that carry a date and a quotation are the ones a human authorized; the rest carry the measurement instead.

Section 05Evidence over assertion: the skill harnesses

A passing test proves nothing on its own. It proves something only when someone has watched it fail for the right reason. This repository has shipped 67 recorded instances of assertions that passed for the wrong reason — including a test that passed with the feature entirely removed. The counter-measure is a set of packaged procedures, invocable by name, that make the expensive-but-correct method the cheap one.

SkillWhat it makes cheapWhy it exists
mutation-replayProving a test guards what it claims, with a scripted red/green replay and a machine-checked verdict.67 recorded assertions that passed for the wrong reason. Its own parser is unit-tested in CI, after it once read a genuinely red focused run as "executed no tests" and announced the wrong verdict.
scratch-postgresStanding up a disposable PostgreSQL cluster carrying the repo's real migrations, to settle an RLS, view, trigger or constraint claim by running it.Database semantics is the one area where careful reading loses to execution most reliably. The recurring pattern is a migration comment asserting something Postgres does not do.
e2e-personasDriving the real app in a real browser as admin, coach, student or parent — against real migrations and real RLS — and reading every write back out of the database.Rendering a control is not the same as saving anything. Constitution item 27 exists because checkers kept being asked the first question.
layout-measurementMeasuring real overflow, wrapping and element widths in a browser at a named viewport.jsdom performs no layout. Every element has zero width, nothing wraps, nothing overflows — so the entire class of responsive bugs is invisible to a 2,000-test suite, and a unit test cannot be evidence for one.
gate-runRunning the six verification gates in one call and printing one evidence block other agents can check.The same six commands are run several times per task by different agents and quoted into logs and PR bodies. One way of running them beats six ad-hoc ways, and stops results being laundered through tail and grep.
linear-task-writingFiling an issue the owner can prioritize and the next agent can implement cold.Constitution item 30. With the ledger frozen, the issue text is the whole record — and 46 rows had migrated in a house style written for the filer rather than the reader.
shared-doc-mergeResolving conflicts in append-only shared documents without losing either side's entry.Several workflows append to the same handful of documents; this resolution happened roughly a dozen times in a single session. Taking one side wholesale silently deletes a real record.
swarm-plan · swarm-run · swarm-checkThe three slash commands that drive planning, a bounded worker/checker loop, and milestone acceptance.The original template surface. Still available, but the natural entry point is now a Linear card rather than a command.

Section 06Intake: Linear as the dispatch queue

The trigger the whole system was designed around, in the owner's words: "part of the integration with Linear over ClickUp is because Linear also has a webhook that would allow me to put an item in the TODO state and trigger Claude to take action." That is now live. On 2026-08-09 the owner dragged an issue to Todo; an agent claimed it 87 seconds later, worked it, and opened a pull request with CI green.

Four constraints that were verified rather than assumed

Free-plan webhooks
Available — confirmed three ways before building, then observed in production. Linear's role gate is satisfied automatically because free-plan members are all admins.
JWT verification
Supabase rejects unauthenticated requests before the function's own code runs, so the function looks dead rather than misconfigured and adding logging produces no new information. Disabled per-function; the platform check is replaced by the HMAC check, not merely removed.
Token identity
The dispatching token must belong to a human GitHub account. The action's human-actor check tests user.type === "User"; an App installation token or machine account resolves to Bot and the run dies before the agent starts, with an error that reads like a configuration problem rather than the identity problem it is.
Silent success
A repository_dispatch that matches no workflow returns 204 — the success code — and only ever runs workflows from the default branch. Testing on a feature branch produces no run and no error.
The bug that would have been invisible

The filter was written to match labels named tier/fast, because every document in the project writes them that way. Linear does not store them that way — it stores a label group named tier with a child named fast, and the slashes are synthesised by the exporter. A prefix match on tier/ would have matched nothing, ever: a queue that never dispatches, a log full of lines each of which looks like a correct decision, and no error anywhere. Caught one commit before shipping, by reading the live workspace instead of the repository's own prose.

Section 07Outbound: replacing semantic automation

The inbound half is signed, filtered and event-driven. The outbound half — how a merged pull request moves the issue — was, until this month, the vendor's built-in automation, which infers intent from text: an issue identifier appearing in a branch name, a pull request title, or beside one of twenty "magic words" in the body. In under 48 hours of that being live, it produced thirteen catalogued wrong state moves across three issues, plus one that was never explained.

ClassWhat went wrongRoot cause
Wrong close ×6Pull requests doing CI salvage, investigation and unrelated work closed an issue none of them touched. One of them opened with the literal sentence "This PR does not close GAM-304."The branch name carried the identifier. That alone links, and a linked PR's merge closes — no magic word required, so omitting one protects nothing.
Backwards move ×2An issue's own fix merging moved it from In Review back to In Progress.State is computed from the aggregate set of linked PRs. With another linked PR still open, the "start" rule outranks the "merge" rule.
Wrong reopen ×3A closed issue reopened because someone opened a PR on a stale branch that still carried its identifier.Branch names outlive the work they were named for.
Silent + misattributedNo notification anywhere in the chain. Automation transitions are attributed to the PR author's mapped user, and attach-time transitions are millisecond-identical with their attachment records.Neither the actor column nor the timestamp distinguishes a human act from an automation firing.

The vendor's own documentation confirms the scoping that would help is impossible: branch rules apply only to target branches, and every pull request here targets main. So no head-branch naming scheme can scope the risk away. Worse, the workaround the project had invented — avoiding identifiers in branch names — cost real process: 11 of 30 recent pull requests are deliberately identifier-free, and prose written about a linking hazard reliably contains the pattern it warns of.

Three things Phase 0 found by accident

While disabling two automations, three further state-writers surfaced that nobody had catalogued. A personal "move to started on branch copy" toggle was on — the likely cause of the one unexplained state move that three investigations had failed to attribute. A workspace commit-linking toggle was off, which is the only reason the project's required commit trailer Linear-Issue: GAM-nnn is inert — it contains linear issue, which is on the vendor's closing magic-word list. And auto-close stale issues was on, at six months, able to cancel a gate/human row on age alone with no pull request, no merge and no human act — which is exactly what that label exists to forbid. Three long-lived owner-gated rows were live exposure. The generalisable lesson is in the document verbatim: this workspace's state-writers are not enumerable from the repository, and three of the four found so far were found by accident.

The proposal itself went through six adversarial review rounds — four independent checkers on the first pass, then five further rounds including two non-Claude reviewers — and the sixth round was explicitly a proportionality review that asked whether the design had drifted. Its verdict is worth quoting as a process outcome: no architecture drift, all five original decisions intact, but moderate over-complication was real and concentrated in guard machinery grown to serve reviewers' threat models rather than observed failures at ten merges a day. Four subsystems were cut on that finding before a line of it was built.

Section 08Continuous verification

Four independent job graphs, split deliberately so a failure names itself rather than hiding inside a generic "CI failed". Three of the four exist because someone found a whole category of tests that nothing was running.

The six gates agents run before opening a pull request

tsc --noEmit · vite build · prettier --check · eslint · the full Vitest suite · a scoped Vitest run for the changed area. They are wrapped in a single skill so that the same six commands, run several times per task by different agents and quoted into logs and PR bodies, produce one comparable evidence block — and so that nobody can launder a result through tail or grep. The format check itself was added after prettier drift landed silently and every subsequent PR merged green while the repository failed its own format:check; typecheck, lint, test and build are all blind to formatting.

Section 09Parallelism, isolation, and a second runtime

Two agent runtimes, one process

The same constitution, ledger, packets, role prompts and verification history drive a second, adjacent implementation lane: OpenAI Codex contributes code to this repository under the identical process. A root AGENTS.md is the adapter. It does not fork the standard — the first line of it is a prohibition on creating a second ledger, constitution, severity scale, or set of role definitions.

What the runtimes shareWhat the adapter translates
The constitution and its 30 items; the Linear queue and item 28's claim protocol; the frozen ledger's provenance; the FAST/STANDARD/HEAVY tiers; the severity scale; the verification and dispute logs; the role charters as portable prose. Role prompts become compact subagent instructions rather than registered agents. Model pins map to two capability tiers — balanced and frontier — with a documented per-role mapping. Claude's hooks become explicit verification commands. And isolation becomes manual: Codex subagents share the filesystem by default, so the orchestrator must create a dedicated worktree and branch and hand the agent that exact path.

Isolation is a rule because sharing a tree corrupted a measurement

Ownership is per file, not per feature

Work is cut into ten user-facing workflows, and which of them can run concurrently is decided by file overlap, not by topic. The project has paid for that lesson twice: two branches once minted the same task number from the same shared file on the same afternoon, and a change correctly scoped to one workflow's own files broke six tests in two other workflows — because the file was a shared loader, whose coupling is invisible from its path.

Coordination ruleThe failure it was written against
One machine owns a file, not a workflow. If two workflows need the same page, the second waits.Five files are documented collision magnets, one of them 4,164 lines with eight open rows touching it.
Branch names are task-scoped — claude/gam-<n>-<slug> — never session-derived.A session-titled branch was used by one session for a PR and, the same afternoon, by another as a working branch: two machines on one mutable ref with nothing announcing the overlap. Caught by the owner asking a question, not by any check.
Before editing anything in the loaders directory, find its importers first — the owning workflow is whoever imports it.A loader that reads like one workflow's territory is called at runtime by three.
Never resolve a shared-document conflict by taking one side wholesale.Both sides are real entries. This has bitten once already, and is now a scripted skill.
The cross-cutting hygiene workflow runs alone — every row in it is a sweep across the whole source tree by definition.It collides with all nine others.

Section 10Observability and cost

Two hooks run inside the agent session itself. A PostToolUse hook lints after every edit or write. A second hook fires after any pull-request merge call and reads the pull request back, because a merge API returning {"merged": true} is the API's word for what it did, not proof the branch landed — this session once reported a PR merged while it was still open. The hook never blocks; it reports, loudly, and when it cannot verify it says so rather than succeeding silently. A SubagentStop hook appends a line every time a worker finishes, recording that a checker is still required.

Beyond the session, the observability story is deliberately cheap and was audited for gaps. A Slack channel receives GitHub workflow events — subscribed explicitly to repository_dispatch, push and schedule, because the default subscription covers pull requests only and would have excluded the dispatch workflow entirely, which is exactly the silent failure the channel exists to end. Linear posts status changes to the same workspace as an independent witness of every state move, including any nobody can attribute.

What it costs, honestly

A note on the dollar figures

Automated runs authenticate against a Claude subscription rather than an API key, so no invoice follows any figure below. The SDK still reports a notional cost by pricing each run's tokens at list rates, and those numbers are kept rather than scrubbed because they are the only quantitative signal available — proportional to tokens weighted by model tier, and therefore sound for comparing one run against another. Read them as consumption, never as spend.

Section 11Honest limits and what is next

A document that only lists what works is the failure mode this project writes rules against. The open items, as the repository itself records them:

  • The outbound sync is designed, reviewed six times, and not built. Phases 0 and 1 shipped; Phase 2 is a filed heavy row that has to pass its own premise gate before a line of it is written. Until then the vendor's merge automation remains the only closer.
  • Nothing tells the owner a dispatch was skipped. The design document calls this its sharpest open item — a wrongly-skipped dispatch currently looks exactly like a quiet week. The Slack notifier that closes it rides with Phase 2.
  • An agent that dies mid-run strands its issue. It sits in In Progress, where the Backlog → Todo webhook can never re-dispatch it. Recovery is a manual re-drag.
  • Attribution is imperfect and will stay so. API-driven transitions attribute to the key owner's user, exactly as the vendor automation's did. The audit comment sitting beside each move is the mitigation; a first-class agent identity is the real fix, and it is a watch item rather than a plan.
  • Two policies live only in workflow comments and owe ratification — the orchestrator's model-by-tier mapping, and the delegation caveat in §2. The constitution reserves amendments to two roles, so a comment does not become a rule by being merged. The repository flags this against itself as an instance of item 20's own failure shape.
  • Documentation drift is tracked, not hidden. One reference guide states a restriction broader than the constitution's, and the disagreement is flagged in place rather than edited away — because narrowing a stated restriction is a governance act, not a documentation fix, and the agent that noticed it had just edited a workflow file.

What this demonstrates

Three things, none of which required a large team or a budget.

Governance can be executable. A constitution that carries its own evidence — the incident, the date, the measurement, the authorizing quotation — is not documentation overhead. It is the onboarding material for every agent that will ever touch the repository, and it is why a cold agent dispatched from a webhook can be trusted to judge its own process tier and defend the call in public.

Verification has to be executable too. Every technique that changed an outcome here came from an agent that ran something — a mutation that had to go red, a throwaway Postgres cluster, a real browser at a real viewport, a prescription executed in an isolated worktree before anyone built it. The techniques that only read code have a much worse record, and the project measures the difference rather than assuming it.

Cost discipline is a design constraint, not an afterthought. Three process tiers, four model tiers, a two-round cap on the most expensive gate, and a proportionality clause that explicitly forbids inflating a finding because its topic sounds serious. The system is built to be affordable enough to actually run — which is the only version of it that produces the 232 verified entries behind this document.
