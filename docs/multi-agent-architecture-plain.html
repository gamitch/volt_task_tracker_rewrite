Engineering architecture note

Nine AI agents build this app under a written constitution

They take work from a Linear board, decide how much process each change gets, and open pull requests. A different agent checks every one. This is how the system works, and what each rule cost to learn.

Repository gamitch/volt_task_tracker_rewrite Subject the development system State of record 11 August 2026

The product is a private attendance and volunteer-hours portal for a high-school robotics team, and it is small. This document covers the system that builds it: nine agent roles with pinned model tiers, a 769-line constitution, three process tiers chosen by risk, six scripted procedures that agents have to run rather than reason about, and a webhook chain that turns a dragged card into a claimed issue and a pull request.

One rule generates most of the others. No agent certifies its own work, and no claim counts as evidence until something ran and someone read the output. Everything below either enforces that or makes it cheap enough to keep doing.

Section 01How work moves

Work crosses three stages. Dragging a card into Todo in Linear starts a run, and nothing else does. An orchestrator then claims the issue, picks a process tier, and delegates to roles that cannot grade themselves. The change then has to survive six local gates, four CI job graphs, and a written record that lands in the same commit as the code.

Section 02The nine roles

Each role is a prompt file in .claude/agents/ with its own tool grant and a pinned model. Nobody picks a model by hand, so a role's cost profile belongs to the role rather than to whoever launched the session. A test checker that shells out to npm run test runs on the cheapest tier available. A reviewer whose job is finding the flaw in someone else's reasoning runs on the most capable one.

boss-arbiterfableread, write, edit, bashDecides worker-versus-checker disputes: redo the work, overrule the checker, call the spec ambiguous, clarify the constitution, or send it to the owner.
foreman-plannersonnetread, write, edit, agentTurns approved plans into small packets and tracks attempts. Also keeps context small by never handing a worker the full record.

Three mechanisms pick the model

They compose, and mixing them up has cost real money.

  1. Frontmatter pins. Spawning a role reads its model: field and applies it. Model selection has always worked in interactive sessions because the pins do it.
  2. A per-dispatch override. Item 18 makes the orchestrator pass model: "opus" on the call when a task creates or edits a migration, an RLS policy or security definer helper, metric-view SQL, or auth and role logic. No config file can hold this, because the trigger depends on what the task turns out to touch.
  3. The orchestrator's own model, set by whoever starts the session. On the automated path it follows the issue's tier label: frontier for heavy and unreviewed, where the tier judgement decides every downstream cost, and balanced for standard and fast.
Delegation can vanish without saying so

All three mechanisms need the orchestrator to be able to spawn subagents. In an automated run, --allowedTools replaces the default tool set instead of extending it, so an allowlist that omits the subagent tool removes delegation. Nothing reports it. The run starts, thinks, works, and returns a plausible result with one model playing every role. On 2026-08-10, issue GAM-304 was dispatched as tier/unreviewed, judged itself HEAVY on an RLS write path, and ran the whole chain on one balanced primary with nothing to delegate to. It died at turn 81 with no branch, no commit, and no pull request. Three constitution items become impossible to satisfy in that state rather than merely skipped, so the tell-tales are now written down: a HEAVY row finishing with no premise-gate verdict, an init line naming one model with no subagent after it, and a row that should have delegated burning through its turn budget.

Section 03Three process tiers, chosen by blast radius

The full chain of packet, premise gate, worker, and checker is expensive, and running it on a one-line fix is how a governed process loses its audience. The owner said as much, and item 26 followed:

For small fixes like items T321 and T323 is there a faster path we can take to get those done? the Boss→Checker→Foreman→Worker→Checker path seems to eat up alot of time for a few line bug fix Human owner, 2026-08-02, authorizing the three-tier model

One question picks the tier, and it has nothing to do with ticket size, topic, or file count: can a mistake here corrupt data, or lie to a user about their own data? The orchestrator states its choice in the pull request and defends it, so a wrong call stays visible.

What the heavy tier has caught

Two cases, both recorded, both invisible to reading the code. On task T305 the premise gate built the proposed fix and captured the real upsert payload, which showed it would null a student's recorded volunteer hours and attendance method. On T189 it showed the proposed detector relied on a view that inner-joins on an active season, so a lapsed season would have told every student their account was deactivated. Both point at the same rule. A gate that only reads is worth much less than one that runs.

Section 04The constitution is an incident log

docs/swarm/constitution.md runs 769 lines. Items 1 through 17 set the project's fixed standards: precedence order, security posture, stack locks, accessibility as a shipping requirement, and a clause banning engagement mechanics because the users are minors and volunteers. Items 18 through 30 work differently. Each one promotes a post-mortem into a rule and carries its evidence, its authorizing date, and the failure it prevents.

The whole set is below. The right-hand column came first in every case.

ItemThe ruleWhat produced it
18 Upgrade the worker's model, per dispatch, for migrations, RLS and security definer helpers, metric-view SQL, and auth and role logic. A silent error in those four places is a data or privacy problem and is hard to detect afterwards. Everywhere else the worker/checker loop costs less than upgrading every worker would.
19 No plan reaches a worker until an adversarial premise checker returns DISPATCH. REVISE is not advisory. A real PRD reached the approval gate carrying two false defect claims, one physically impossible prescription, one "fix" that would have stripped accessible names off six screens, and a silent reversal of a passed task's green test. Someone who did not write it already checked every other artifact in the process. Plans were the exception.
19a The gate stops after two rounds. A third REVISE goes to the owner. Round 1 cost roughly 130K frontier tokens and caught 4 BLOCKERs. Round 2 cost roughly 105K and caught 2 MAJORs. One round costs about one prevented rework cycle, so two rounds break even and a third loses. A plan still failing after two rounds has a problem the wording cannot fix.
19d Every heavy packet ends with three to five numbered least confident decisions, each naming the decision and what would make it wrong. The gate attacks that list first. About half of round 1's findings were the author's own unverified line numbers and claims, which means the author was already in a position to know where the weak ground was. Declaring a doubt costs nothing and counts against nobody. Concealing one costs a gate round.
20 A deliberate deferral files a task. A code comment does not count. Two team pickers shipped rendering fixture data, because each task correctly declined out-of-scope wiring and recorded that in a comment. events.team_ids is uuid[] and the fixture ids were plain strings, so the deferral turned into meeting creation failing outright in production. A light/dark toggle shipped inert the same way. Nobody triages comments.
21 Completion reports name a commit SHA, and someone verifies HEAD moved. "Clean" and "committed" are separate claims. A worker reported "final state confirmed clean" alongside an accurate account of 770 changed lines, live browser measurements at three viewports, and every command it ran. All of it was real and none of it was committed. Routine worktree cleanup would have destroyed the work. An empty diff against the merge base is what contradicted the report.
22 Stage named paths. No git add -A or git add ., by any agent, ever. A subagent modified a source file without authorization during a documentation commit. A habitual git add -A would have swept that into a commit whose message described packet authoring, with no packet defining it, no checker verifying it, and the owner away. Staging too broadly bypassed three safeguards at once. The edit itself was a harmless fixture rename.
23 Mutation experiments run in the agent's own worktree. A dirty tree is not proof of an unauthorized change. A premise gate ran four instrumented mutations against the shared tree, intending to revert each. The orchestrator found the tree dirty mid-experiment, reverted it, and blamed a different agent that was behaving correctly. One missing convention produced three failures. Mutation proofs have caught more real defects here than any other technique, so the rule isolates the practice instead of discouraging it.
24 The ledger row and the verification entry go into the merge commit itself. Records were backfilled accurately at 11:39. Five tasks merged over the next ten hours and no row moved, so the document the owner reads before merging still said "packet gated" for work already live. A gate had flagged the gap explicitly and nobody acted on it. A separate recording step is the step that gets dropped under pressure.
25 Grade security findings against this threat model: one volunteer team, no PII stored. A finding about view semantics became a security-class task on two bad steps. The orchestrator read a table-scoped rule as covering views, then graded its own extension as blocker-adjacent. The leaderboard shows everyone's hours by design, so the "exposure" was the feature, and the task closed as no-change. The owner ruled: "This is a volunteer group, not a company... please keep it simple."
26 Pick FAST, STANDARD, or HEAVY by risk, then state and defend the choice in the pull request. The full chain was consuming hours on few-line fixes. Stating the tier in public makes a wrong call correctable instead of silent.
27 A user-visible surface reading from a fixture is Partial, never Passed, and the wiring task is filed before the row moves. Item 20's three failures all passed a checker, because each checker was asked whether the component rendered and never whether it was connected to anything. Packets for user-visible work now name the real data source as an acceptance criterion, so the checker follows the data.
28 Take work from Linear's Todo column, claim it first, then re-read the issue to confirm you hold it. The first agent dispatched through Linear found its issue unaided and then did not claim it. The agent was not at fault: the constitution contained the word "Linear" zero times. The migration moved 296 rows of data and left the protocol behind. Linear has no compare-and-set, so the claim is a hope without the read-back.
29 The 301-row markdown ledger is frozen. Linear allocates ids atomically, and a script generates the git-side record. A single audit found three independent failures in the same table: merged, tested, live work with no row at all; a workflow document claiming 40 open rows against a true 50; and eleven rows recording their closure in the wrong column while Status still read "Filed", so an agent worked a row superseded four days earlier. Every edit read correctly to a human. This is what a schema-less table does at 301 rows and four concurrent machines.
30 Every issue an agent writes goes through the linear-task-writing skill: lead with the defect, defend a priority, re-verify every citation, keep the original when rewriting. The owner's words are the rationale: "i have to know which ones to prioritize and i can't understand what it's saying." Rewriting the trigger issue also surfaced three errors nobody had caught: a wrong line number, a second render site that does not exist, and a missing root cause that would have sent the implementer to a helper the render path no longer calls.

Each of these rules is cheap to state and was expensive to learn. Writing the incident into the rule stops the next agent, or the next engineer, from re-litigating it, and it lets the constitution serve as the whole onboarding packet for an agent arriving cold. Rules carrying a date and a quotation are the ones a human authorized. The rest carry the measurement.

Section 05Six procedures agents have to run

A passing test counts as evidence only after someone has watched it fail for the right reason. This repository has shipped 67 recorded assertions that passed for the wrong reason, including a test that passed with the feature entirely removed. The counter-measure is a set of packaged procedures, invocable by name, that make the correct method the cheap one.

SkillWhat it makes cheapWhy it exists
mutation-replayProving a test guards what it claims, through a scripted red/green replay and a machine-checked verdict.67 recorded assertions that passed for the wrong reason. Its own parser is unit-tested in CI, after it read a red focused run as "executed no tests" and returned the wrong verdict.
scratch-postgresStanding up a disposable PostgreSQL cluster with the repo's real migrations, to settle an RLS, view, trigger, or constraint claim by running it.Careful reading loses to execution most reliably in the database. The pattern that keeps recurring is a migration comment asserting something Postgres does not do.
e2e-personasDriving the real app in a browser as admin, coach, student, or parent against real migrations and real RLS, then reading every write back out of the database.Rendering a control and saving something are different claims. Item 27 exists because checkers kept being asked about the first one.
layout-measurementMeasuring real overflow, wrapping, and element widths in a browser at a named viewport.jsdom performs no layout. Every element has zero width, nothing wraps, and nothing overflows, so the whole class of responsive bugs is invisible to a 2,000-test suite and a unit test cannot be evidence for one.
gate-runRunning the six verification gates in one call and printing one evidence block other agents can check.Different agents run the same six commands several times per task and quote them into logs and pull request bodies. One way of running them beats six, and it stops results being laundered through tail and grep.
linear-task-writingFiling an issue the owner can prioritize and the next agent can implement cold.Item 30. With the ledger frozen the issue text is the whole record, and 46 rows had migrated in a house style written for the filer.
shared-doc-mergeResolving conflicts in append-only shared documents without losing either side's entry.Several workflows append to the same few documents, and this resolution came up roughly a dozen times in one session. Taking one side wholesale deletes a real record.
swarm-plan · swarm-run · swarm-checkThree slash commands driving planning, a bounded worker/checker loop, and milestone acceptance.The original template surface, still available. A Linear card is now the usual entry point.

Section 06Linear dispatches the work

The owner wanted one thing from the tracker: "part of the integration with linear over clickup is because linear also has a webhook that would allow me to put an item in the TODO state and trigger claude to take action." That works now. On 2026-08-09 the owner dragged an issue to Todo, an agent claimed it 87 seconds later, worked it, and opened a pull request with CI green.

Four constraints, verified rather than assumed

Free-plan webhooks
Available. Confirmed three ways before building, then observed in production. Linear's role gate clears automatically, because free-plan members are all admins.
JWT verification
Supabase rejects unauthenticated requests before the function's own code runs, so the function looks dead rather than misconfigured and adding logging tells you nothing new. It is disabled per function, and the HMAC check replaces the platform check rather than merely removing it.
Token identity
The dispatching token has to belong to a human GitHub account. The action's human-actor check tests user.type === "User", so an App installation token or machine account resolves to Bot and the run dies before the agent starts, with an error that reads like a configuration problem.
Silent success
A repository_dispatch matching no workflow returns 204, the success code, and only ever runs workflows from the default branch. Testing on a feature branch produces no run and no error.
A bug that would have been invisible

The filter was written to match labels named tier/fast, because every document in the project writes them that way. Linear stores a label group named tier with a child named fast, and the exporter synthesises the slashes. A prefix match on tier/ would have matched nothing, ever: a queue that never dispatches, a log full of lines that each look like a correct decision, and no error anywhere. Reading the live workspace instead of the repository's own prose caught it one commit before shipping.

Section 07Replacing the outbound automation

The inbound half is signed, filtered, and event-driven. The outbound half, which moves the issue when a pull request merges, was the vendor's built-in automation until this month, and it infers intent from text: an issue identifier in a branch name, a pull request title, or beside one of twenty magic words in the body. Inside 48 hours it produced thirteen catalogued wrong state moves across three issues, plus one nobody has explained.

ClassWhat happenedCause
Wrong close ×6Pull requests doing CI salvage, investigation, and unrelated work closed an issue none of them touched. One opened with the sentence "This PR does not close GAM-304."The branch name carried the identifier. That alone links, and a linked pull request's merge closes, so omitting a magic word protects nothing.
Backwards move ×2An issue's own fix merging moved it from In Review back to In Progress.State is computed from the aggregate set of linked pull requests. With another linked PR still open, the start rule outranks the merge rule.
Wrong reopen ×3A closed issue reopened when someone opened a pull request on a stale branch still carrying its identifier.Branch names outlive the work they were named for.
Silent and misattributedNothing in the chain sends a notification. Automation transitions attribute to the author's mapped user, and attach-time transitions are millisecond-identical with their attachment records.Neither the actor column nor the timestamp separates a human act from an automation firing.

Linear's documentation rules out the scoping that would help: branch rules apply only to target branches, and every pull request here targets main. The workaround the project invented, keeping identifiers out of branch names, cost real process. Eleven of the last thirty pull requests are deliberately identifier-free, and prose written about a linking hazard reliably contains the pattern it warns of.

Three state-writers Phase 0 found by accident

Disabling two automations surfaced three more nobody had catalogued. A personal "move to started on branch copy" toggle was on, and it is the likely cause of the one unexplained state move that three investigations failed to attribute. A workspace commit-linking toggle was off, which is the only reason the project's required commit trailer Linear-Issue: GAM-nnn stays inert: it contains linear issue, one of the vendor's closing magic words. Auto-close stale issues was on at six months, able to cancel a gate/human row on age alone with no pull request, no merge, and no human act, which is what that label exists to forbid. Three long-lived owner-gated rows were live exposure. The document states the lesson plainly. This workspace's state-writers are not enumerable from the repository, and three of the four found so far were found by accident.

The proposal went through six adversarial review rounds, starting with four independent checkers and ending with two non-Claude reviewers. The sixth round asked whether the design had drifted. Its verdict: no architecture drift, all five original decisions intact, but moderate over-complication was real and concentrated in guard machinery grown to serve reviewers' threat models rather than observed failures at ten merges a day. Four subsystems were cut on that finding before anyone built a line of it.

Section 08What CI checks

Four independent job graphs run on every push and pull request, split so a failure names itself rather than hiding inside a generic "CI failed". Three of the four exist because someone found a category of tests that nothing was running.

The six gates agents run before opening a pull request

tsc --noEmit, vite build, prettier --check, eslint, the full Vitest suite, and a scoped Vitest run for the changed area. One skill wraps them, so the same six commands produce one comparable evidence block no matter which agent runs them, and nobody can launder a result through tail or grep. The format check joined the list after prettier drift landed silently and every subsequent pull request merged green while the repository failed its own format:check. Typecheck, lint, test, and build are all blind to formatting.

Section 09Running machines in parallel

Two runtimes, one process

OpenAI Codex contributes code to this repository under the same constitution, ledger, packets, role prompts, and verification history. A root AGENTS.md adapts the mechanics. It opens with a prohibition on creating a second ledger, constitution, severity scale, or set of role definitions.

Shared by both runtimesTranslated by the adapter
The constitution and its 30 items. The Linear queue and item 28's claim protocol. The frozen ledger's provenance. The three tiers, the severity scale, the verification and dispute logs, and the role charters as portable prose. Role prompts become compact subagent instructions rather than registered agents. Model pins map to two capability tiers, balanced and frontier, with a documented per-role mapping. Claude's hooks become explicit verification commands. Isolation becomes manual, because Codex subagents share the filesystem by default, so the orchestrator creates a worktree and branch and hands the agent that path.

Isolation became a rule after a shared tree corrupted a measurement

One machine owns a file

Work is cut into ten user-facing workflows, and file overlap decides which can run at once. The project has paid for that twice. Two branches minted the same task number from the same shared file on one afternoon, and a change correctly scoped to one workflow's files broke six tests in two others, because the file was a shared loader whose coupling is invisible from its path.

Coordination ruleThe failure behind it
One machine owns a file, not a workflow. If two workflows need the same page, the second waits.Five files are documented collision magnets. One runs 4,164 lines with eight open rows touching it.
Branch names are task-scoped, claude/gam-<n>-<slug>, never session-derived.A session-titled branch served one session's pull request and, the same afternoon, another session's working branch. Two machines shared one mutable ref with nothing announcing it. The owner caught it by asking a question.
Before editing anything in the loaders directory, find its importers. Whoever imports it owns it.A loader that reads like one workflow's territory is called at runtime by three.
Never resolve a shared-document conflict by taking one side wholesale.Both sides are real entries. This has bitten once, and a scripted skill now handles it.
The cross-cutting hygiene workflow runs alone.Every row in it sweeps the whole source tree by definition, so it collides with all nine others.

Section 10Watching it, and what it costs

Two hooks run inside the agent session. One lints after every edit or write. The other fires after any pull-request merge call and reads the pull request back, because a merge API returning {"merged": true} reports what the API did rather than proving the branch landed. This session once reported a pull request merged while it was still open. The hook never blocks, it reports loudly, and when it cannot verify it says so instead of succeeding quietly. A third hook appends a line whenever a worker finishes, recording that a checker is still required.

Outside the session, a Slack channel receives GitHub workflow events, subscribed explicitly to repository_dispatch, push, and schedule. The default subscription covers pull requests only and would have excluded the dispatch workflow, which is the exact silent failure the channel exists to end. Linear posts status changes to the same workspace as an independent witness of every state move, including any nobody can attribute.

Section 11Open problems

Listing only what works is the failure shape this project writes rules against, so the repository's open items follow.

  • The outbound sync is designed, reviewed six times, and unbuilt. Phases 0 and 1 shipped. Phase 2 is a filed heavy row that has to pass its own premise gate before anyone writes it. The vendor's merge automation remains the only closer until then.
  • Nothing reports a skipped dispatch. The design document calls this its sharpest open item, because a wrongly-skipped dispatch looks exactly like a quiet week. The Slack notifier that closes it ships with Phase 2.
  • An agent that dies mid-run strands its issue in In Progress, where the Backlog → Todo webhook can never re-dispatch it. Recovery is a manual re-drag.
  • Attribution stays imperfect. API-driven transitions attribute to the key owner's user, exactly as the vendor automation's did. The audit comment beside each move is the mitigation. A first-class agent identity would fix it properly, and it is a watch item.
  • Two policies live only in workflow comments and owe ratification: the orchestrator's model-by-tier mapping, and the delegation caveat in section 2. The constitution reserves amendments to two roles, so a merged comment is not a rule. The repository flags this against itself as an instance of item 20.
  • One reference guide states a restriction broader than the constitution's. The disagreement is flagged in place rather than edited away, because narrowing a stated restriction is a governance act, and the agent that noticed it had edited a workflow file that same session.

The next concrete step is Phase 2: build scripts/linear-sync.mjs, its workflow, the CI declaration gate, and the reconciliation sweep, run the sync in shadow mode until it matches the incumbent on ten consecutive real merges plus three staged control pull requests, then make the declaration check required and verify it blocks before disabling the last automation.
